# MuseFlow 最终产品设计文档

- 版本：v1.1
- 文档状态：目标基线
- 更新日期：2026-09-24
- 产品定位：一个以 Python 后端工程为主体、以 AI 图像生成为业务场景的可靠任务平台

## 1. 文档目的

本文定义 MuseFlow 从已完成 MVP 演进到最终作品集版本的产品方向、功能边界和验收标准，作为后续需求取舍与实施规划的共同基线。

MuseFlow 不以堆叠模型能力或技术栈为目标。项目选择 AI 图像生成这一真实业务场景，重点解决第三方 AI 服务耗时长、接口不稳定、执行结果需要持久化以及异步任务需要可靠恢复等工程问题。

已完成 MVP 的详细范围和历史验收标准继续保留在 [MuseFlow MVP 产品设计文档](./museflow-mvp-product-design.md) 中；本文不覆盖该阶段记录。

除本文明确改写的内容外，MVP 已发布的可靠性契约继续有效。最终版本特别继承 HTTP 幂等的 200/201/409 语义、线性手动重试、外部 Provider 可能重复调用和重复计费的降级承诺，以及默认最多 3 个 attempt、10 分钟任务总截止时间。运行策略可以在有真实证据时调整，但必须按任务保存 `policy_version` 和策略快照，不能通过重启或修改环境变量让既有任务语义漂移。

## 2. 产品定位

MuseFlow 的一级用户是希望评估或复现后端工程能力的面试评审者和开发者；本地图片生成体验者是次级用户。产品提供文生图与单参考图条件生成任务的创建、异步执行、状态追踪、故障恢复和结果管理能力。

项目的核心价值不是替代专业图片创作产品，而是证明：一个外部 AI 模型能力可以被接入为可靠、可测试、可部署的 Python 后端系统。

最终版本重点展示两类能力：

- **Python 后端工程**：API 设计、数据建模、异步任务、幂等、并发控制、故障恢复、对象存储、测试与部署。
- **AI 应用工程**：真实模型服务接入、Provider 契约、生成参数与参考素材建模、错误归一化、结果校验和成本边界。

## 3. 目标用户与使用场景

### 3.1 目标用户

- 希望在 15–30 分钟内评估项目后端设计、实现和可靠性证据的面试官与代码评审者；
- 希望在本地复现 AI 生成任务及故障场景的开发者；
- 需要验证文生图或单参考图条件生成完整流程的本地体验者；
- 项目维护者本人，用于持续积累 AI 应用开发与 Python 后端实践。

### 3.2 核心使用场景

1. 用户输入提示词，创建一个文生图任务。
2. 用户上传单张参考图片并输入提示词，创建一个单参考图条件生成任务。
3. 系统立即接受任务，在后台调用图片生成 Provider。
4. 用户查看任务阶段、attempt、重试情况、错误和执行时间线。
5. 临时失败由系统自动重试，永久失败进入可诊断终态。
6. 用户对符合规则的失败任务发起手动重试。
7. 用户在历史记录中查看任务、参考图片、生成结果和重试链。
8. 评审者通过 MockProvider 确定性复现成功、超时、限流、临时失败和永久失败。

## 4. 产品目标与成功定义

### 4.1 产品目标

- 跑通“提示词或参考图片 → 创建任务 → 异步生成 → 可靠恢复 → 保存结果 → 查询和下载”的完整链路。
- 用统一任务模型表达文生图和图生图，同时保留不同生成能力的明确约束。
- 在第三方 AI 服务超时、限流、临时异常和 Worker 中断时，使任务自动恢复或进入可诊断终态。
- 保护任务、参考素材和生成结果的一致性及访问边界。
- 通过 Mock 场景、自动化测试、真实 Provider 验收和可复现部署证明项目声明。
- 让项目描述中的每一项功能和性能数据都能从代码、测试或验收记录中得到支撑。

### 4.2 成功定义

最终版本成功意味着：评审者能够按照 README 使用一条 Docker Compose 启动命令在干净环境中启动完整前后端，分别完成一次文生图和单参考图条件生成任务，观察主要故障与恢复场景，并检查到与产品声明一致的测试和验收证据。

用户增长、商业变现、生成质量领先、模型训练能力和公网高可用不属于本项目的成功指标。

## 5. 产品原则

1. **可靠性优先于功能数量**：新增生成能力必须复用并验证现有任务可靠性机制，不能绕过状态机和结果管理链路。
2. **事实优先于演示效果**：展示真实阶段、attempt 和错误，不使用无法解释的虚假进度百分比。
3. **一个可信纵向切片优先于大而全平台**：完成文生图和图生图，不扩张为视频、音频或工作流编排产品。
4. **业务事实以数据库为准**：队列、缓存和前端状态不能成为任务最终状态的唯一来源。
5. **能力声明必须可验证**：未完成真实接入或可复现测试的功能、性能和可靠性指标不得写入对外材料。
6. **外部服务边界必须诚实**：不把 Provider 无法保证的外部 exactly-once 包装成本系统承诺。

## 6. 最终功能范围

### 6.1 图像生成

- 支持文生图和单参考图条件生成两种任务类型；后者在 API 和数据模型中仍使用稳定枚举 `IMAGE_TO_IMAGE`。
- 文生图以提示词和受控生成参数作为输入。
- 单参考图条件生成以提示词、单张参考图片和受控生成参数作为输入。MuseFlow 保证将经过验证的确切图片字节提交给明确支持该能力的 Provider，但不承诺视觉相似度、审美质量或编辑精度。
- 每个任务生成一张图片，生成尺寸和文件格式采用白名单约束。
- 至少接入一个经过真实端到端验证的图片生成 Provider。
- 保留确定性的 MockProvider，用于自动化测试和故障演示。
- Provider 不支持某项能力时，创建任务前返回明确的能力错误，不在执行阶段静默降级。
- 图生图正式实现前必须完成独立的 Provider 阶段 0，核对官方契约并在逐次授权和费用上限内完成一次真实成功探针；探针失败时停止实施并重新选择 Provider 或缩减产品承诺。

### 6.2 参考素材管理

- 支持上传图生图所需的单张参考图片。
- 对文件大小、媒体类型、文件头和图片尺寸进行服务端校验。
- 参考图片保存到私有对象存储，数据库记录对象标识、文件类型、大小、尺寸和校验和。
- 创建图生图任务时引用已经成功保存且仍然有效的参考素材。
- 参考素材不能通过公开对象地址直接访问；受信网络内的 MuseFlow API 可以签发短期访问地址，但最终版本不提供用户级素材授权或所有权隔离。
- 上传接口要求 `Idempotency-Key`：同键同文件返回原素材，同键不同内容返回冲突。
- 参考素材使用 `STAGING → READY | FAILED` 生命周期；进入删除流程时使用 `READY → DELETE_PENDING → DELETED`。
- 超过 1 小时的 `STAGING` 素材必须自动恢复或清理。未被任务引用且超过 24 小时的 `READY` 素材只进入 dry-run 报告和显式管理命令，不在核心版本中自动删除；被任务引用的参考素材随任务保留。

### 6.3 任务管理

- 幂等创建文生图和图生图任务。
- 查询任务主状态、执行阶段、attempt、时间线、错误和结果。
- 使用稳定 cursor 分页查看历史，并支持按任务类型和状态筛选。
- 对符合规则的失败任务发起手动重试，并展示线性重试链。
- 手动重试复用原任务的规范化输入；修改提示词、参考图片或参数属于新建任务。
- 一个 attempt 表示一次逻辑 Provider 生成调用。lease 接管、已有远端请求的继续轮询、参考素材临时读取失败和结果持久化恢复均留在同一 attempt；只有再次创建远端生成请求时才增加 attempt。
- 任务创建时冻结 Provider profile、模型、能力版本和运行策略版本，凭据仍只从运行环境注入。
- 终态不可逆，最终版本不支持取消正在执行的 Provider 请求。

### 6.4 异步执行与故障恢复

- API 接受任务后立即返回，不阻塞等待模型生成。
- PostgreSQL 保存任务、attempt、事件、投递意图和结果元数据，并作为业务事实源。
- Scheduler 负责可靠投递、到期重试和过期执行租约回收。
- Worker 使用带 execution token 条件的 lease heartbeat 和 fencing。生成结果先写入不可变候选对象，只有当前权威 execution token 可以在数据库中发布唯一结果指针；过期 Worker 不能覆盖权威对象或结果元数据。
- 对网络超时、限流和可恢复服务异常执行有上限的自动重试。
- 对参数错误、能力不支持和内容安全拒绝等永久错误停止自动重试。
- 重复 HTTP 请求和重复队列消息不能产生多个逻辑任务或多个权威结果。
- Scheduler 的核心热循环不得执行 MinIO 网络 I/O；素材恢复和候选对象清理通过隔离的维护任务执行。

### 6.5 Provider 接入

- 通过统一 GenerationProvider 契约隔离业务逻辑与供应商协议。
- Provider 适配器负责请求转换、远端状态轮询、错误分类和结果定位。
- Provider 内部不得执行会绕过平台 attempt 语义的隐式创建重试。
- API 与 Worker 使用同一份只读 Provider capability registry。静态能力不支持在创建时返回 4xx，当前部署缺少所选 profile 返回 503，运行时超时、限流和可恢复 5xx 才进入任务重试。
- 真实 Provider 的地区、模型、费用、超时、结果主机和幂等边界必须形成可追踪记录。
- 第二个真实 Provider 属于优先扩展项，用于进一步验证适配层，但不是图生图交付成立的前置条件。

### 6.6 结果管理

- 生成结果保存到私有对象存储，数据库保存经过验证的结果元数据。
- 第三方结果必须经过主机、重定向、网络地址、响应大小、媒体类型、文件头和图片尺寸校验后才能入库。
- 第三方结果经过验证后写入以内容摘要标识的不可变候选对象。数据库元数据通过 execution token fencing 指向获胜候选后，任务才能进入成功终态。
- 前端使用稳定的 MuseFlow 下载入口，不持久化底层对象存储签名地址。
- 下载通过短期签名 URL 或等价机制完成。匿名直读 MinIO 必须失败；由于核心版本没有认证，能访问 MuseFlow API 且知道素材 ID 的调用方可以取得短期下载入口。

### 6.7 前端体验

最终版本保持轻量前端，只服务于任务流程验证：

1. **创建任务**：选择文生图或图生图，填写提示词；图生图额外上传并预览参考图片。
2. **任务详情**：查看输入摘要、参考图片、阶段、attempt、时间线、错误、重试链和生成结果。
3. **任务历史**：按任务类型和状态筛选，分页浏览并进入任务详情。

前端默认通过轮询更新非终态任务。只有在真实体验或负载数据证明轮询成为问题后，才评估 SSE；不为展示技术栈而引入实时通道。

### 6.8 测试、观测与演示

- 单元测试覆盖任务状态、错误分类、重试策略和 Provider 契约。
- PostgreSQL、Redis、Worker、Scheduler 和 MinIO 关键链路具有集成测试。
- 文生图和图生图的创建、执行、查询、失败与结果访问具有端到端测试。
- MockProvider 能确定性触发主要成功和故障场景。
- 至少保留一次文生图和一次图生图的受控真实 Provider 验收记录。
- 记录任务排队时间、执行时间、attempt 数量、错误类型和终态结果，支持问题诊断。
- 最终核心版本不对外声明并发量、吞吐量或 P95，因此压测不是发布门。只有决定在 README、简历或演示中公开性能数字时，固定环境、固定场景、原始结果和对应 commit 才同时成为发布门。

## 7. 核心业务流程

```text
选择文生图或图生图
    ↓
填写提示词；图生图上传并选择参考图片
    ↓
校验输入并幂等创建任务与投递意图
    ↓
返回 task_id 与 QUEUED
    ↓
Scheduler 可靠发布消息
    ↓
Worker 获取执行租约并调用对应 Provider 能力
    ↓
┌────────────────────┴────────────────────┐
↓                                         ↓
Provider 成功                             调用失败
↓                                         ↓
安全下载并验证结果                  分类为临时或永久错误
↓                                  ┌──────┴──────┐
写入不可变结果候选                  ↓             ↓
↓                              等待自动重试     FAILED
携带 execution token 发布权威指针
↓
SUCCEEDED
```

## 8. 信任边界与安全约束

- 最终版本默认运行在本机或受信网络，不得直接暴露到公网；不提供调用者身份鉴别、素材所有权或用户隔离。
- 对象存储保持私有，参考图片和生成结果不得使用长期公开 URL。匿名直读 MinIO 必须失败，但受信网络内的 MuseFlow API 本身不要求登录。
- 日志不得记录密钥、完整签名 URL、原始 Provider 响应或不必要的用户输入内容。
- 上传内容和第三方下载内容都必须由服务端验证，不能信任文件扩展名或响应声明。
- Provider 凭据只通过运行环境注入，不进入源码、前端、镜像或版本库。
- 若未来需要公网部署，必须把认证、用户隔离、配额、限流和费用保护作为一个独立产品阶段整体设计。

## 9. 范围边界

### 9.1 最终版本必须具备

- 文生图与图生图完整纵向链路；
- 参考图片的安全上传、私有存储和任务关联；
- 上传幂等、参考素材状态机、超时 `STAGING` 自动恢复，以及未引用 `READY` 素材的 dry-run/显式清理能力；
- 可靠异步执行、自动重试、lease heartbeat、不可变候选结果、fencing 和结果唯一性保护；
- 至少一个真实 Provider 与 MockProvider；
- 任务历史、详情、手动重试和结果访问；
- 一条 Docker Compose 命令可复现启动完整前后端；
- 自动化测试、故障演示和真实 Provider 验收证据。

### 9.2 优先扩展项

- 第二个真实图片 Provider，用于验证统一适配层；
- 仅在对外声明性能数字时执行的可复现压测、运行指标和容量说明；
- 未引用 `READY` 素材的自动 TTL 删除、用户删除 API 和任务级删除；
- 在有明确证据时使用 SSE 改善状态更新体验。

### 9.3 明确不做

- 视频生成、FFmpeg 转码、音频生成和广义多模态理解；
- 模型训练、微调、LoRA、数据标注和算法效果研究；
- 节点式工作流、图片编辑画布、蒙版编辑和专业创作工具；
- 多图融合、批量生成和不受约束的高级模型参数；
- 智能 Provider 路由、自动故障转移和复杂熔断平台；
- 为小规模图片上传预先建设分片上传和断点续传；
- 为展示技术栈而增加热点缓存、WebSocket、微服务或 Kubernetes；
- 未配套认证、隔离、配额和费用保护的公网部署；
- 未经验证的外部 exactly-once、并发量、吞吐量和 P95 承诺。

## 10. 演进路线

### 已完成基线：可靠文生图 MVP

- 文生图任务创建、异步执行、状态查询和结果访问；
- GenerationProvider、真实图片 Provider 与 MockProvider；
- PostgreSQL、Scheduler、Redis、Celery 和 MinIO 可靠链路；
- 幂等、attempt、lease、fencing、自动重试和手动重试；
- 创建、详情和历史页面，以及 MVP 自动化验收。

MVP 是历史交付基线，不代表其中所有实现都无需加固。最终版本首先修复固定结果对象键与 lease 上界造成的并发一致性缺口。

### 阶段 0：真实图生图 Provider 门禁

- 使用官方资料冻结地域、账号权限、模型、费用、输入限制、轮询协议、结果主机和外部幂等边界；
- 在单独授权和明确费用上限内完成一次单参考图真实成功探针；
- 探针不通过时停止后续实现，改选 Provider 或降低产品承诺。

### 阶段 1：可靠性加固

- 使用不可变候选对象和数据库权威指针闭合对象存储 fencing；
- 增加 lease heartbeat、稳定执行阶段和错误分类；
- 补齐新旧 Worker 交错写、lease 过期和维护任务故障隔离测试。

### 阶段 2：参考素材纵向切片

- 增加上传幂等、参考素材状态机、服务端校验、私有存储和任务关联；
- 实现超时 `STAGING` 自动恢复，以及未引用 `READY` 素材的报告和显式清理；
- 保持既有文生图数据、接口和下载路径兼容。

### 阶段 3：单参考图条件生成

- 定义文生图与图生图统一但明确区分的任务输入；
- 扩展 Provider 契约、Mock 场景和正式 Adapter；
- 将加固后的可靠性机制复用于图生图任务；
- 补齐正式前端、Compose 交付、自动化测试和真实 Provider 验收。

### 阶段 4：证据化收尾

- 完善任务指标、错误分类、架构图和演示脚本；
- 建立产品验收条目到测试、受控验收记录或人工检查的追踪表；
- 整理 README、当前测试结果和对外描述；
- 仅在决定公开性能数字时执行固定条件下的可复现压测。

第二真实 Provider、SSE、自动 TTL 删除或公网能力必须在核心版本稳定后独立评估，不与图生图纵向切片捆绑交付。

## 11. 最终验收标准

以下条件全部满足后，才能声明 MuseFlow 最终作品集版本完成：

1. 在干净环境中按 README 使用一条 Docker Compose 命令启动完整前后端。
2. 通过正式前端完成一次文生图任务和一次单参考图条件生成任务。
3. 图生图参考图片经过传输大小、实际格式、文件头、完整解码、尺寸、总像素、帧数和色彩模式校验，并保存于私有对象存储。
4. 上传使用幂等键；同键同文件返回原素材，同键不同内容返回冲突。
5. 文生图和图生图任务均复用相同的可靠投递、逻辑 attempt、lease heartbeat、fencing 和重试机制。
6. MockProvider 可以稳定演示成功、临时失败后成功、限流、超时、永久失败和已有远端请求的恢复。
7. 重复 HTTP 请求、重复消息以及产生不同结果字节的新旧 Worker，不会生成多个逻辑任务或破坏唯一权威结果；数据库 checksum 必须与获胜对象一致。
8. Redis 短暂离线、Worker 中断、服务重启和 MinIO 暂时不可用后，非终态任务能够在版本化策略规定的上限内自动恢复或进入可诊断终态。
9. 创建任务与显式删除素材并发时，不会产生引用 `DELETE_PENDING`、`DELETED` 或缺失对象的任务。
10. 超时 `STAGING` 素材可以自动恢复或清理，未引用 `READY` 素材可以生成 dry-run 报告并通过显式命令安全清理。
11. 匿名直读 MinIO 中的参考图片与结果失败；受信网络内可通过无用户认证的 MuseFlow API 获得短期下载入口，README 明确说明这一边界。
12. API 与 Worker 使用同一 Provider capability registry，任务冻结 Provider profile、模型、能力版本和策略版本；配置漂移不会导致静默切换。
13. 至少一个真实 Provider 的文生图和图生图端到端验收记录可复查，并保留外部可能重复调用和重复计费的降级说明。
14. 既有 MVP 数据能够升级，旧创建请求继续默认为文生图，旧任务和下载路径保持有效。
15. 新旧 Worker 交错、lease 过期、创建与清理并发、上传重放、Provider 配置漂移、超大 multipart 和含历史数据迁移均有自动化测试。
16. 后端和前端直接相关的测试、lint、类型检查、数据库迁移检查、构建及 Compose 验证全部通过。
17. README 能让评审者理解定位、无认证边界、启动方法、演示方式、资源上限和已知限制。
18. 产品验收追踪表把每一项声明映射到自动化测试、受控真实验收、Compose 演示或明确人工检查，并记录对应 commit；没有证据的条目不得标记完成。

## 12. 验收证据类型

| 证据类型 | 适用内容 | 最低要求 |
| --- | --- | --- |
| 自动化测试 | 领域规则、幂等、并发、恢复、迁移和 API 契约 | 测试名称、运行命令和当前 commit |
| 受控真实验收 | Provider 地域、权限、真实协议、结果主机和收费调用 | 日期、模型、受控参数、脱敏结果及单次授权 |
| Compose 演示 | 干净环境启动、完整前后端和主要故障场景 | 一条启动命令、复现步骤和已知限制 |
| 人工检查 | README、架构图、简历描述和敏感信息审查 | 检查清单、检查人或执行记录和对应 commit |

### 12.1 验收追踪基线

下表定义每项最终验收必须提供的证据入口。实施完成前状态均视为“未证明”；各阶段交付时填写实际测试文件、记录路径、运行日期和 commit。

| ID | 验收主题 | 必需证据 |
| --- | --- | --- |
| P-01 | 一条 Compose 命令启动完整前后端 | Compose config、镜像构建、健康检查与干净环境演示记录 |
| P-02 | 正式前端完成两类任务 | Playwright Mock 流程与真实 Provider 受控记录 |
| P-03 | 参考图片安全校验 | 单元测试、原始 multipart API 测试与 MinIO 集成测试 |
| P-04 | 上传幂等 | API 201/200/409 测试与 PostgreSQL 并发测试 |
| P-05 | 两类任务复用任务生命周期 | Worker/Scheduler 集成测试与架构检查 |
| P-06 | Mock 故障场景 | 确定性 Provider 契约测试与 Playwright 演示 |
| P-07 | 唯一权威结果 | 新旧 Worker 不同字节交错写入测试与对象 checksum 核对 |
| P-08 | 故障后有界收敛 | Redis、MinIO、Worker 和进程重启故障注入测试 |
| P-09 | 创建与删除并发安全 | PostgreSQL 锁协议和外键集成测试 |
| P-10 | 素材恢复与显式清理 | maintenance queue 集成测试、dry-run 与管理命令记录 |
| P-11 | 私有存储和无认证边界 | MinIO 匿名 403、短期入口测试与 README 人工检查 |
| P-12 | Provider profile 冻结 | registry 单元测试、启动校验和 API/Worker 漂移测试 |
| P-13 | 真实 Provider E2E | 单次授权、脱敏请求轨迹、结果摘要和对应 commit |
| P-14 | MVP 兼容迁移 | 含历史数据的 Alembic 升级、旧 API 和旧下载回归测试 |
| P-15 | 发布阻断竞态 | 第 15 项列举场景的自动化测试集合 |
| P-16 | 工程质量门 | 测试、lint、类型检查、迁移检查、构建和 Compose 命令输出 |
| P-17 | README 可复现性 | 干净环境人工演示记录和已知限制检查 |
| P-18 | 对外声明一致 | README、简历和产品声明逐项核对记录 |

性能数据只有在决定公开时才进入追踪表；没有公开吞吐量、并发量或 P95 时，不要求为了完成版本而运行 Locust。
