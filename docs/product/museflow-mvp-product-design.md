# MuseFlow MVP 产品设计文档

- 版本：v0.2
- 阶段：MVP 发布验收完成
- 更新日期：2026-09-18
- 项目定位：面向开发者和面试评审者的 AI 异步任务可靠性作品集

## 1. 产品概述

MuseFlow 是一个在本机或受信网络运行的 AI 图像生成任务平台。用户提交提示词后，系统创建异步任务、调用一个真实图片生成 Provider，并提供状态查询、自动恢复、手动重试、结果访问和历史记录能力。

MVP 的首要目的不是验证个人创作者市场，也不是与成熟图片创作产品竞争，而是通过一个可运行、可测试、可复现的纵向系统，展示 Python 后端、第三方 AI 服务接入、异步任务和故障恢复设计能力。

## 2. 目标与成功定义

### 2.1 产品目标

- 跑通“输入提示词 → 创建任务 → 异步执行 → 保存结果 → 查询和下载”的完整链路。
- 让用户看到真实可验证的执行阶段、attempt、时间和错误，不展示虚假进度百分比。
- 对超时、限流、临时服务异常、消息丢失和 Worker 中断提供可测试的自动恢复能力。
- 对 HTTP 重放、消息重复投递和过期 Worker 回写提供明确的幂等与并发保护。
- 通过 Docker Compose 提供可复现的本地演示环境。
- 每一项写入 README 或简历的可靠性声明都必须有实现或可复现测试记录支撑。

### 2.2 成功定义

MVP 成功意味着：在干净环境中能够按 README 启动系统，使用 `MockProvider` 稳定复现成功与主要故障场景，并至少完成一次受控的真实 Provider 端到端生成。系统在约定的故障窗口内能够自动恢复或进入可诊断终态，不依赖操作者执行正常恢复命令。

用户增长、留存、生成质量竞争力和商业转化不属于本阶段成功指标。

## 3. 目标用户与信任边界

### 3.1 目标用户

MVP 的首要用户是：

- 希望了解项目架构与可靠性设计的开发者；
- 面试官、代码评审者和技术作品集浏览者；
- 在本地运行项目、验证功能和故障场景的项目维护者。

### 3.2 信任边界

- MVP 仅允许在本机或受信网络中运行。
- MVP 不提供账号、认证、用户隔离、配额、计费和公网滥用防护。
- README 必须明确声明：不得将当前版本直接暴露到公网。
- 对象存储仍保持私有，结果只能通过短期签名 URL 访问。

若未来需要公网部署，认证、授权、数据隔离、调用限额和费用保护必须作为新的产品阶段设计，不能通过隐藏按钮或网络约定替代。

## 4. 核心场景

1. 用户输入提示词并提交任务。
2. API 立即返回任务编号和 `QUEUED` 状态，不等待模型生成。
3. 用户查看任务的当前阶段、attempt、重试次数和时间线。
4. Worker 调用 Provider 并把验证后的单张结果保存到对象存储。
5. 任务成功后，用户通过短期签名地址查看或下载结果。
6. 临时失败由系统自动重试；永久失败直接进入终态。
7. 符合条件的失败任务可以手动创建一个关联的新任务。
8. 用户通过历史记录查看任务、结果和重试链。
9. 在 Demo 模式下，评审者可以确定性地创建成功、限流、超时、临时失败和永久失败场景。

## 5. 核心流程

```text
输入提示词
    ↓
幂等创建任务并写入投递意图
    ↓
返回 task_id 与 QUEUED
    ↓
Scheduler 发布消息
    ↓
Worker 获取执行租约并调用 Provider
    ↓
┌──────────────┴──────────────┐
↓                             ↓
Provider 成功                 调用失败
↓                             ↓
验证并保存单张结果       ┌────┴───────────┐
↓                        ↓                ↓
SUCCEEDED          临时失败并等待重试   永久失败
                         ↓                ↓
                    RETRY_WAIT          FAILED
```

## 6. MVP 功能范围

### 6.1 图像生成

- 支持文生图。
- 请求只包含提示词和一个尺寸预设。
- 提示词原样保存，长度为 1–2000 个字符；纯空白输入无效。
- 每个任务固定生成一张图片。
- 尺寸预设在阶段 0 根据真实 Provider 的实测结果确定。
- 不向用户暴露模型、seed、负面提示词、采样器或质量档位。
- 接入一个真实图片生成 Provider。
- 提供确定性的 `MockProvider`，用于普通测试和故障演示。

### 6.2 任务管理

- 幂等创建生成任务。
- 使用稳定 cursor 分页查看任务历史，并支持按状态筛选。
- 查看任务参数、主状态、当前阶段、attempt、时间线、错误和结果。
- 对符合规则的失败任务发起手动重试。
- 查看原任务与手动重试任务形成的线性重试链。

### 6.3 异步执行与自动恢复

- 图片生成由独立 Worker 执行，API 请求不等待生成结束。
- PostgreSQL 保存任务、attempt、重试时间和投递意图，并作为业务事实源。
- Scheduler 负责发布待处理消息、调度到期重试和回收过期执行租约。
- 对网络超时、HTTP 429 和可恢复 5xx 执行有限次数自动重试。
- 参数错误、内容安全拒绝和不支持的请求不自动重试。
- 非终态任务必须最终自动恢复执行或进入可诊断终态。
- 正常恢复流程不得依赖人工运行恢复命令。

### 6.4 结果管理

- 生成结果保存到私有对象存储，数据库保存对象标识、验证后的文件类型、大小和校验和。
- 任务只有在结果对象与数据库元数据均确认后才能进入 `SUCCEEDED`。
- 结果下载通过有效期为 5 分钟的签名 URL。
- 支持 PNG、JPEG 和 WEBP，单个结果对象默认不超过 20 MiB。
- 对第三方结果执行主机、重定向、超时、大小和文件头校验。
- MVP 不提供删除 API 和自动数据 TTL；数据保留到操作者显式执行开发环境重置。

### 6.5 最小前端

MVP 建设三个页面：

1. **创建任务**：填写提示词并提交。
2. **任务详情**：查看阶段、attempt、时间线、错误、重试链和结果。
3. **任务历史**：按稳定 cursor 分页浏览任务，并进入详情或重试允许的失败任务。

前端通过轮询更新非终态任务。`SUCCEEDED` 或 `FAILED` 后停止轮询；不引入 WebSocket 或 SSE。

## 7. 状态、attempt 与重试规则

### 7.1 任务主状态

```text
QUEUED → RUNNING → SUCCEEDED
             ├──→ RETRY_WAIT → QUEUED
             └──→ FAILED
```

- `QUEUED` 表示系统已接受并承诺执行，不等同于消息此刻已经位于 Redis。
- `RUNNING` 表示某个 Worker 持有有效执行租约。
- `RETRY_WAIT` 表示已确认临时失败，并等待数据库记录的下一次执行时间。
- Worker 崩溃或执行租约过期时，任务可以由 Scheduler 重新进入 `QUEUED`。
- `SUCCEEDED` 和 `FAILED` 是不可逆终态。
- MVP 不支持取消任务。

### 7.2 自动重试

- 自动重试属于同一个业务任务。
- 每次已确认的 Provider 调用对应一个 attempt。
- Worker 崩溃后的接管继续恢复同一个未决 attempt，不因重新抢占自动增加 attempt sequence。
- 只有收到已分类的临时错误后，才创建下一个 attempt。

默认策略：最多 3 次 attempt，包括首次调用；采用指数退避、full jitter 和 10 分钟任务总截止时间。具体时间参数由技术方案约束。

### 7.3 手动重试

- 手动重试创建新的业务任务，并以 `retried_from_task_id` 指向原失败任务。
- 一个失败任务最多产生一个直接手动重试任务，重试关系形成线性链。
- 新任务复制原任务的规范化请求，不能通过 retry 接口修改参数。
- 修改提示词或其他参数属于创建新任务。
- 原失败任务保持终态，不执行 `FAILED → RUNNING` 逆向转换。

允许手动重试：临时错误耗尽、Provider 暂不可用、内部结果保存失败、任务截止时间耗尽，以及操作者已经修复的 Provider 配置错误。

禁止手动重试：参数错误、不支持的请求和内容安全拒绝。

## 8. 幂等与结果唯一性承诺

### 8.1 HTTP 幂等

- 创建任务和手动重试必须携带 `Idempotency-Key`。
- 单用户 MVP 中幂等键采用全局作用域，并与任务保存同样久。
- 同键、同规范化请求返回原任务，不再次创建投递意图。
- 同键、不同请求返回 `409 IDEMPOTENCY_KEY_CONFLICT`。
- 新任务返回 `201 Created`；幂等重放返回 `200 OK`，并标明 `idempotency_replayed: true`。

### 8.2 重复消息与外部调用

MuseFlow 承诺：

- 一个幂等 HTTP 请求只创建一个逻辑任务；
- 重复消息不会产生多个权威成功结果；
- 过期 Worker 不能覆盖当前执行者的结果；
- 终态任务不会再次执行。

MuseFlow 只有在真实 Provider 支持客户端幂等键，或允许按客户端预先确定的稳定请求标识查询和恢复时，才承诺避免故障窗口中的外部重复调用。仅在提交后返回且无法重建的服务端 request ID 不足以消除“远端已受理、本地尚未保存 ID”的窗口。若阶段 0 不能找到满足条件的 Provider，产品承诺必须降级为“保证一个权威本地结果，但极端故障窗口可能产生重复外部调用或费用”。

## 9. Demo 模式

Demo 模式显式启用后，系统额外提供不属于正式产品契约的任务创建入口。评审者可以选择：

- `success`；
- `transient_then_success`；
- `rate_limited`；
- `timeout`；
- `permanent_failure`。

场景作为内部执行 profile 持久化，不通过特殊提示词触发。非 Demo 模式不注册该入口。

## 10. 产品信息架构

```text
React 前端
    ↓ HTTP / JSON
FastAPI API
    ↓
PostgreSQL：任务、attempt、事件、结果元数据、outbox
    ├── Scheduler：outbox 发布、到期重试、租约回收
    │       ↓
    │     Redis Broker
    │       ↓
    └── Celery Worker → GenerationProvider
                ↓
              MinIO
```

系统采用模块化单体：API、Worker 和 Scheduler 共享同一代码库与领域规则，但作为不同进程角色运行。MVP 不拆分微服务。

## 11. 非目标

- 参考图、图生图、视频生成和多模态理解。
- 多图生成、任意尺寸、复杂生成参数和质量评测。
- 多个真实 Provider、智能路由和自动故障切换。
- 用户注册、认证、RBAC、用户隔离、配额和计费。
- 公网部署和公网滥用防护。
- 任务取消、删除 API 和自动数据 TTL。
- WebSocket、SSE 和事件流平台。
- 文件分片上传、断点续传和用户素材管理。
- 微服务、Kubernetes、跨地域部署和高可用。
- 备份恢复与灾难恢复承诺。
- 完整 tracing、metrics 和可观测平台。
- 未经压测验证的并发量、吞吐量或 P95 指标。
- Provider 不支持幂等或结果恢复时的外部 exactly-once 承诺。

## 12. 发布验收标准

以下项目全部通过后，才能声明 MVP 完成：

1. 干净环境按 README 完成迁移并启动全部服务。
2. `MockProvider` 成功任务端到端完成并保存一张结果。
3. HTTP 同键同请求返回原任务，同键不同请求稳定返回 409。
4. Redis 离线时任务仍可靠记录，恢复后 outbox 自动投递。
5. 同一消息重复投递不会产生多个权威结果。
6. Worker 在 Provider 调用前、Provider 接受后和对象上传后中断，任务均能自动收敛。
7. 两次临时失败后成功；永久失败不自动重试。
8. 最大 attempts 和任务总截止时间均生效。
9. 手动重试形成线性任务链，禁止重试规则由服务端执行。
10. API、Worker、Scheduler 和 Redis 重启后，状态与结果保持一致。
11. MinIO 对象不可公开读取，下载使用短期签名 URL。
12. 日志检查未发现密钥、完整签名 URL、提示词或原始 Provider 响应。
13. 三个前端关键流程通过 Playwright。
14. lint、类型检查、单元测试、集成测试和端到端测试全部通过。
15. 至少一次受控真实 Provider 冒烟测试有日期、版本和结果记录。

## 13. 交付约束与阶段

- 开发资源：一名开发者。
- 完整目标：六周。
- 第四周末必须形成可独立交付的后端作品集，不通过删除故障测试伪装完成。
- 日常测试全部使用 Mock；真实 Provider 只做显式启用的受控冒烟测试。

阶段 0 必须先形成 Provider 可行性记录，验证地区与账号、费用、客户端幂等或按客户端稳定标识恢复、超时、错误结构、结果获取和结果主机。详细实施顺序见技术方案。

## 14. 后续演进方向

MVP 稳定并完成证据化验收后，再独立评估：

1. 公网部署所需的认证、隔离、配额和费用保护。
2. 第二个真实 Provider，用于验证适配层是否具备真实扩展价值。
3. 参考图和图生图工作流。
4. SSE 状态推送。
5. 数据删除、保留策略和备份恢复。
6. 指标、追踪、压测和容量规划。

这些方向不属于 MVP 完成条件。
