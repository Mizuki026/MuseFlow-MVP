# MuseFlow MVP 产品设计文档

- 版本：v0.1
- 阶段：MVP 方向确认
- 项目定位：面向 AI 应用开发与 Python 后端能力展示的图像生成任务平台

## 1. 产品概述

MuseFlow 是一个 AI 图像生成与异步任务编排平台。用户提交提示词和可选参考图后，系统以异步任务调用图片生成模型，并提供状态查询、结果管理、失败重试和历史记录能力。

MVP 不追求成为完整的多模态创作平台，而是重点解决 AI 生成任务耗时长、第三方服务不稳定、执行状态难追踪和图片结果需要持久化等问题。

## 2. 产品目标

- 跑通从输入、任务创建、异步执行到结果访问的完整链路。
- 让用户能够清楚了解任务处于排队、执行、成功或失败中的哪一阶段。
- 对超时、限流和临时服务异常提供可控的自动恢复能力。
- 保证重复提交、重复消费等情况下不会产生不可控的重复任务或结果。
- 提供可测试、可复现、可通过 Docker Compose 一键启动的项目交付物。
- 通过项目重点展示 Python 后端、AI 服务接入、异步任务和可靠性设计能力。

## 3. 目标用户与使用场景

### 3.1 目标用户

MVP 面向需要调用 AI 图片模型完成生成任务的个人用户或开发者。首版采用单用户演示模式，不建设完整账号与权限系统。

### 3.2 核心场景

1. 用户输入提示词，并可选上传一张参考图。
2. 用户提交生成任务，页面立即返回任务编号，不等待模型生成完成。
3. 用户查看任务状态和执行进度。
4. 任务成功后，用户查看或下载生成图片。
5. 任务失败后，用户查看错误原因，并在允许的情况下手动重试。
6. 用户通过历史记录查看此前的任务及结果。

## 4. 核心流程

```text
输入提示词 / 上传参考图
            ↓
        创建生成任务
            ↓
     返回 task_id 和状态
            ↓
   Worker 异步调用图片模型
            ↓
   ┌────────┴────────┐
   ↓                 ↓
生成成功          生成失败
   ↓                 ↓
保存并展示结果    展示错误 / 重试
```

## 5. MVP 功能范围

### 5.1 图像生成

- 支持文生图。
- 支持可选参考图输入，为后续图生图能力保留入口。
- 支持少量必要参数，例如图片尺寸和生成数量；MVP 默认一次生成一张。
- 接入一个真实图片生成服务。
- 提供一个可模拟成功、超时、限流和永久失败的 `MockProvider`。

### 5.2 任务管理

- 创建生成任务。
- 分页查看任务历史。
- 查看单个任务的状态、参数、执行时间、重试次数、错误和结果。
- 对符合条件的失败任务发起手动重试。
- 使用幂等键避免用户重复点击产生重复任务。

### 5.3 异步执行与失败恢复

- 图片生成由独立 Worker 异步执行，API 请求不等待生成结束。
- 对网络超时、HTTP 429 和临时服务异常执行有限次数的自动重试。
- 重试采用指数退避和随机抖动，避免短时间集中请求第三方服务。
- 参数错误、内容安全拒绝、认证失败等永久错误不自动重试。
- 自动重试耗尽后，任务进入失败状态并保留可诊断的错误信息。

### 5.4 素材与结果管理

- 参考图和生成结果保存到对象存储。
- 数据库保存对象标识、文件类型、大小和关联任务等元数据。
- 使用有有效期的签名 URL 上传和访问文件。
- 对上传文件的类型和大小进行基础校验。

### 5.5 最小前端

MVP 只建设三个主要页面：

1. **创建任务**：填写提示词、上传参考图并选择必要参数。
2. **任务详情**：查看状态、重试次数、错误信息和生成结果。
3. **任务历史**：分页浏览任务，并进入详情或重试失败任务。

前端通过轮询更新任务状态，暂不引入 WebSocket 或 SSE。

## 6. 任务状态与核心规则

任务状态采用以下主流程：

```text
CREATED → QUEUED → RUNNING → SUCCEEDED
                           ↘ FAILED
```

- PostgreSQL 中的业务任务记录是状态的唯一事实来源。
- Redis 和 Celery 负责消息传递与任务执行，不直接替代业务状态存储。
- 状态只能按允许的方向流转，非法状态转换必须被拒绝并记录。
- Worker 重复消费同一任务时，不得重复调用模型或生成多份有效结果。
- 手动重试必须保留与原失败任务的关联，便于追踪任务历史。

## 7. 产品信息架构

```text
React 前端
    ↓
FastAPI API
    ├── PostgreSQL：任务、重试和文件元数据
    ├── Redis：Celery 消息代理
    ├── Celery Worker：执行生成和重试
    ├── MinIO：参考图与生成结果
    └── GenerationProvider：真实模型 / MockProvider
```

MVP 采用模块化单体架构，保持模块边界清晰，但不提前拆分微服务。

## 8. 非目标

以下能力不属于本次 MVP：

- 视频生成、视频处理和 FFmpeg 流程。
- 多个真实模型供应商及复杂模型路由。
- 多模态理解、生成质量评测和候选排序。
- 用户注册、复杂权限和 RBAC。
- 用户配额、计费、令牌桶限流和热点缓存。
- WebSocket 或 SSE 实时推送。
- 文件分片上传、断点续传和哈希去重。
- Kubernetes、微服务拆分和复杂熔断系统。
- 未经真实压测得到的并发量或 P95 性能指标。

## 9. MVP 完成标准

- `docker compose up` 可以启动 API、Worker、PostgreSQL、Redis 和 MinIO。
- 至少一个真实图片模型能够完成端到端生成。
- 创建任务后立即返回任务编号，并可持续查询状态。
- 输入图片和生成结果能够正常上传、保存和访问。
- 使用 `MockProvider` 可以稳定演示成功、超时重试和永久失败。
- 相同幂等键的重复请求不会创建重复任务。
- 重启 API 后任务历史和结果仍然存在。
- 核心单元测试和集成测试全部通过。
- README 能让新用户在较短时间内理解、启动并演示项目。
- 简历中的功能和性能描述均有实际实现或测试记录支撑。

## 10. 后续演进方向

MVP 稳定后，再根据实际价值逐步考虑：

1. 接入第二个真实 Provider，验证模型适配层的扩展能力。
2. 增加用户配额、限流和模型调用成本统计。
3. 使用 SSE 推送任务状态，替代前端轮询。
4. 增加更完善的可观测性和压测报告。
5. 在独立迭代中探索视频生成和更复杂的多模态工作流。

这些方向不作为 MVP 完成的前置条件。
